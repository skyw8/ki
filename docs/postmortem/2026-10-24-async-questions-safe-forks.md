# 异步问题不能复用阻塞 UI，旁聊不能直接 fork 最新节点

## 背景

实现 `request_user_input_async` 时，需要让主任务继续运行，同时支持用户稍后打开问题、
进行旁聊并明确提交答案。这暴露出两个容易混淆的边界：问题的持久状态与一次工具调用的
生命周期不同；可复制的 jsonl 前缀与可交给模型的协议历史也不同。

这是一篇实现前调研发现的陷阱及对应防护记录，不是线上数据丢失事故。

## 根因与风险

- extension `ui.confirm/select` 是有超时的同步 Host RPC，内存槽以 session/kind/extension
  标识。它既不能寻址多个同类问题，也不能在重启后恢复，不能当成异步问题的事实来源。
- assistant tool-call 消息会先落盘，工具结果随后才到。busy fork 的显式 `entryId` 只说明
  节点存在，不保证所有并行 tool call 都有 result。直接复制最新节点可能产生非法模型请求。
- 用户可能很晚才打开问题。若此时才计算 fork 点，旁聊会混入主任务后续发现，改变原问题的
  语境，也无法解释刷新前后为什么回答不同。
- “答案已接收”和“答案已进入模型上下文”之间存在取消、崩溃和队列消费竞态。先标记
  answered 再尝试投递，会让尚未进入历史的输入看起来已经送达。
- side session 复用 fork 不等于复用 subagent。后者还有身份、调度容量与自动完成回灌，
  会把用户的独立讨论误当成代理任务。
- 缓存亲和不等于权限隔离，也不保证共享前缀命中。为保留父缓存而继续暴露写工具，会破坏
  旁聊只读约束；只在提示词声明只读又不足以强制工具能力。

## 防护原则

1. 提问整批验证，先写持久问题事实，再发事件和返回 `{"accepted":true}`；不等待用户。
2. 接受提问时固定来源和安全历史引用。安全边界必须包含完整的 tool call/result 配对；
   当前批次未完成则退回批次之前，不等待长工具结束。
3. 问题与必要的当前 user 内容作为独立背景补充，不伪造缺失 toolResult。首次旁聊消息才
   创建 session，但不重新选择父 leaf；主任务后续推进不改变快照。
4. 答案保留 question 和 submission 身份，持久接收投影为 answer_queued；对应的 typed
   user entry 真正提交后才是 answered。恢复根据事实协调，不能假设多个文件天然原子。
5. 旁聊是独立 purpose、run、SSE、停止作用域和可见历史边界，不自动注入主对话；
   用户最后确认的答案才交付父模型。
6. 只读工具声明和执行边界同时生效，路径与符号链接也受约束。合法的缓存亲和可以继承，
   但父 run、WebSocket 续传和 response 身份不能继承。

## 实现审查发现与修复

- `EvalSymlinks` 后通过 pathname 启动 rg 仍存在根目录或祖先被替换的竞态，`--no-follow`
  不能约束显式搜索根。旁聊搜索改用逐层核验并固定的 `os.Root`，目录枚举与内容读取均
  通过该根；使用有文件、字节、时间与结果预算的 RE2 / glob 搜索，不运行外部搜索进程。
- 只过滤模型工具不足以隔离扩展。warmup、reload、输入、消息结束、生命周期通知及独立
  compact 路径均需跳过旁聊扩展钩子，普通 session metadata 不能伪造旁聊来源。
- 同一 submission ID 用于不同问题会触发 Inbox 去重，丢掉第二条答案；服务端在接受前
  原子拒绝跨题复用。工具 call ID 也不能假定跨轮全局唯一，重试必须匹配来源与完整问题。
- 资源快照逐题或逐修订复制会放大存储，甚至写入超过扫描器上限的 JSONL 行。现在每批只
  保存一次私有快照，更新保存公开增量，写前校验大小；公开列表和历史索引不保留资源正文。
- 分支切换不撤销全局首次答案回执；单独派生当前分支是否包含答案，避免历史回答自动重投。
- 旁聊子会话已落盘而问题关联未写回时，重试必须按来源与问题找回原子会话；内存锁不能
  替代重启恢复。冻结 CWD 及复制补充用户附件同样不能推迟到首次旁聊时重新选择来源。

## 会话切换与布局修正

后续界面验证发现，问题栏为大屏预留左侧 224px 导致消息整体右移；改为独立浮层，
打开 / 关闭均不改变消息滚动容器几何。问题投影增加来源 session 身份，runtime / tail
不能合并另一会话的问题。进一步复现确认：同级 QuestionsRail 与 RequestNav 均使用 session ID
作 key，违反同级唯一性；重复加载时旧节点可能残留，阴影逐次叠加并保留失效点击回调。
给 main 加 key 只能掩盖跨会话残留，不能解决同会话重载，现已删除该补丁，分别使用
`questions:` 与 `requests:` key；重复点击已选会话不再清空重载，保留滚动与问题栏状态。

侧栏原来只枚举已经创建的旁聊，提问后尚无 child 就不可展开。公开缓存行补充 `questionLinks`
作为惰性讨论入口；它不创建会话、不提交答案。创建后按问题 ID 与真实 child 去重、自动展开来源。
全局问题事件同步非当前会话入口，修订号拒绝旧事件，在途列表遇到新事件重新读取，避免旧响应覆盖。
首次旁聊的 effect 与发送路径不再重复 select/recover，以免互相取消；关闭窗口后的已创建关联仍刷新侧栏。
双会话、重复点击、后台事件与延迟列表浏览器用例覆盖这些生命周期。

后续验证：问题交互与会话状态联合 24 个浏览器用例通过，保留过期请求与 ACK 重放断言；
相关 Question/List 的 Go race 检查通过。最终全量 `go test -tags embed -count=1 ./...`
于 66.28 秒通过。期间一条既有 Markdown 缩放用例单跑通过，随后全量重跑通过；未重启
当前服务，未进行真实模型验收。

旁聊输入复用普通 composer 卡片与发送 / 中断样式，移除额外整理草稿控件。历史快照仍
冻结，模型改为跟随来源当前 provider/model/thinking：空闲时同步，忙碌旁聊下一轮同步，
不在生成中改写配置。

## 列表冷启动回退

公开问题入口最初直接在 ListCache 中调用 QuestionsAt，导致每个会话先加载完整 transcript，
即使没有问题也解析全部历史并估算 token。功能回归使用短历史和热缓存，未覆盖启动时的真实
历史规模。182 个会话、约 733 MB 历史的独立进程测量中，基础 List 为 32 ms，冷 ListCache
为 13.92 s；CPU 采样确认 QuestionsAt/ReadTranscript 占约 81% 样本。前端 Promise.all 又
推迟提交 workspace，使约 17 ms 返回的 workspace 也呈现为长时间加载。

修正为基础行同步读取、问题导航独立版本化摘要与后台增量追赶；列表不再触碰聊天 transcript
缓存。全局锁缩到行索引，按会话合并重建，两个 worker 限制后台并发。workspace/session
独立加载、报错、重试与按范围刷新。追赶期间保留本地更高修订入口，最终摘要再删除失效入口。

184 个会话、约 758 MB 的隔离副本测量：无摘要基础列表 31 ms，后台约 5.98 s 完成；
已有摘要的新缓存读取 308 ms，热读取 8 ms。该测量为本机文件缓存条件，非冷盘或网络验收。
缓存损坏/更高版本、部分末行、截断、分支与答案校验的 Go race 回归，以及阻塞/失败的两类
列表与 pending 摘要浏览器回归覆盖此路径。最终 14 个问题/列表浏览器用例通过，
session/server 完整 race 检查通过，全量 `go test -tags embed -count=1 ./...` 于 72.32 s 通过。

## 提交后保留答题表单

最初确认后用纯文本回执替换表单，隐藏了模型提供的未选项，也丢失“选项 + 补充内容”的
展示结构。现在继续使用原表单：所有选项和选中状态保持可见，radio 禁用，文本只读且可复制。
确认时额外保存 `answerForm` 的原始选项与文本，服务端验证拼接结果等于实际答案并保持
首次接受不可改写；重开和跨窗口从持久回执恢复，不能依赖仍可能未提交的本地草稿。
仅有答案正文的记录按完整选项边界恢复，不能确定的内容作为自由答案显示。

浏览器回归还暴露了两处测试初始化竞态。侧栏助手原来只等 session 列表就开始展开，
workspace 请求较晚返回时会把“尚未出现工作区”当成“已经全部展开”；现在同时等待独立的
workspace 就绪状态。刷新答题回执的测试原来在页面启动后才改写 fixture 并发送事件，
初始化请求可能先捕获默认 pending 状态，而 SSE 也可能尚未订阅。测试现在在刷新前保存
回执，并由 fixture 初始化同步恢复，确保后续 GET 和事件读取同一状态，不依赖调度顺序。

## 子代理首次请求缓存回退

会话 `01a16bf9365d71b0881db298c9fb8939` 的三个后期子代理首次请求分别出现
187857 / 0、91178 / 0、91170 / 15744 的 prompt / cache-read token；后续请求恢复稳定缓存。
对比实际 `request_header`，主会话与 child 的 system 只差异步提问工具清单和 guidance，
工具 schema 同样只差 `request_user_input_async`。即使继承 cache affinity，删除这个工具
也改变 system 开头和 schema，导致整段复制历史失去共享前缀。之前的测试只比较 child 与
更深 child，它们都删除同一工具，因此没有发现主会话到 child 的差异。

普通子代理改为保留共享 schema 与 system，description 和 child user 信封明确仅主会话
可提问，host callback 继续在执行时强制拒绝 child，不能写入问题事实。只读旁聊仍使用
独立受限工具集合。回归比较主会话、child 和更深 child 的完整 system/schema，并通过
实际模型工具调用验证主会话成功、child 返回 main-only 错误且没有创建问题。
检查 child 命中率时还需排除复制的父历史，避免把父 miss 重复计为每个 child 的新 miss。

## 回归方向

覆盖并行工具批次提问、主任务继续、延迟首次旁聊、压缩与重启恢复、跨 tab 重复提交、
接受后取消、分支切换和越界读 / 写工具拒绝。UI 还需覆盖预选不提交、关闭不取消旁聊、
整理稿不自动覆盖及不自动回传。

核对通过；全量 `go test -tags embed -count=1 ./...`（含 WebUI）66.24 秒通过。
问题 / 路径相关 Go race 检查通过。Web unit 从 326 项 / 4.08 秒增为 338 项 / 4.21 秒。

64 MiB 超限写入拒绝检查，其编码成本予以保留。没有重启运行中的服务，也未调用真实
