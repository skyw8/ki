# 请求导航落点与灰色选中项不一致

日期：2026-09-27

## 现象

右侧请求列表有时需要连续点几次才到正确位置；手机上更明显。灰色项不一定是刚选中的请求，重新打开面板后还可能残留另一个灰色项。长会话包含未加载历史、可变行高和 compact 折叠，放大了这些问题。

## 根因

- 选中计算使用 `getOffsetForIndex(index, 'start')`，它返回经过最大 scrollTop 限制的滚动目标。靠近底部的多个短请求共享一个目标值，二分查找因此把它们误认成同一个位置，通常选到更晚的请求。
- 点击后只调用一次 `scrollToIndex` 就清除目标；虚拟行、正文补全与 Markdown 的实际高度还会继续改变。没有持有稳定 key，也就没有完整的落点与选中生命周期。
- 点击前遗留的触摸方向和自动翻页预算没有清除，程序滚动可能被当作此前手势的延续。
- 完整回归另暴露较早折叠行展开时的竞争：关闭 following 并不会取消虚拟库已经发出的 scrollToEnd，后续协调仍能改写阅读位置。进入显式阅读时还需用当前 scrollTop 替换未完成的目标。
- 普通导航条目的 `offsetTop` 相对于定位祖先，虚拟条目相对于列表；原代码把两者都直接当列表坐标。手机浏览器还会在点按后保留 `:hover`，产生第二个看似选中的灰底。
- 原落点测试只断言 `<96px`，一个已经滚到视口上方的负数也能通过；没有覆盖列表尾部、反复往返和慢速分页改点。

## 修复

1. 阅读选中使用真实、未夹到末尾的行起点，并与列表统一过滤非人类 origin。跟随尾部时选择最新请求。
2. 显式跳转保留目标 key，连续两帧到达可达位置后结束；后续高度变化继续补偿目标上方内容。短尾部请求保持所选项，不制造额外空白。真实读者手势或回到底部释放该选择。
3. 跳转清除旧方向、翻页预算、惯性标记和未完成的末尾滚动目标。加载历史时立即显示目标，新点击、取消或切会话使旧导航失效；失败不能留下虚假的选中项。
4. 导航自身滚动使用相对矩形坐标；触屏点击关闭面板前先恢复触发按钮焦点，避免浏览器随后自动滚动。hover 底色仅作用于精细鼠标，触控按钮/条目采用 44px，虚拟估高与之保持一致。Escape 恢复焦点，条目支持方向键和 Home/End。

## 回归

- 45 条不同高度请求：桌面和 390px 触屏单击往返，断言目标可见、可达落点误差不超过 2px、只有目标 aria-selected，并在真实阅读手势后更新。
- 原最早请求测试增加落点下界，不能再让负数误过。
- 9 轮工具密集的 compact 历史：先点击尚未加载的第 0 轮，卡住首个分页，再点击第 3 轮；放行后必须停在最后所选轮，不能被旧请求拉回，且不继续拉无关的旧页。
- 请求导航和恢复用例加入 Firefox / WebKit 滚动项目；响应式矩阵与独立滚动性能预算继续约束触控布局、主线程停顿和内容漂移。

浏览器仿真可以验证状态与几何，不宣称覆盖真机 Safari 的软键盘动画、系统冻结与原生惯性全部细节。

最终验证（2026-09-27）：类型检查与构建通过；`go test -tags embed -count=1 ./...` 全部通过，含 117 条浏览器场景且无跳过；Firefox / WebKit / iPhone UA 的三个滚动项目共 54 条通过。较早折叠行的聚焦复测连续 5 次通过。

单独运行 `cd web && bun run test:perf`：6 条通过。长历史两轮滚动采样均无 long task，翻页锚点保持 `60px → 60px`；桌面、长历史、手机 CPU 4× 的流式提交 p95 分别约 35.9 / 36.0 / 34.3ms。数字是本机单次测量，不代表真机帧率或网络延迟承诺。

真实开发服务重启后，使用原始 session `01a0e2d7fd137920b51b08f44ca4f650` 的完整历史，在 390px 触屏布局中单次点击第 1、5、8 条请求，落点和选中均正确；回前台协调后的阅读位置偏移为 0px，页面无异常。

## 教训

“请求的身份”“内容的真实位置”“浏览器允许到达的位置”是不同的值。底部 clamp 后的位置不能用于识别请求。虚拟列表的跳转是一次要等待测量稳定、允许后续手势接管的交互，不能以发出滚动命令作为完成。
