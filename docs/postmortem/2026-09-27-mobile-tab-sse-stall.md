# 手机恢复后仍停在旧消息：重连不等于正文追平

日期：2026-09-27

关联 session：`01a0e2d7fd137920b51b08f44ca4f650`。

## 现象与修复经过

会话记录中，用户先报告手机长时间离开后页面像掉线、通知却能收到；随后两次反馈修复没有效果。最有区分度的复现是：“sleep 20s 收到了通知，进去还是旧消息，要手动刷新”。

第一轮修改加了服务端心跳对应的 45s 客户端读空闲守卫，以及 push 连接的生命周期重连。第二轮发现 20s 未达到空闲阈值，又增加“隐藏超过 2s 且期间没收到字节”的恢复规则。其测试只证明新的 `/v1/events` 请求出现，没有证明打开的聊天已经显示最终答案。

这次检查保留了已有守卫、退避、计时显示改动，修复恢复链路中遗漏的数据协调，并扩大回归断言。

## 根因

Web Push 通知与页面 SSE 是两条独立通道；能收到通知不证明页面拿到了最终消息。流式 fetch 可能既没有新字节也不抛错，客户端需要读空闲守卫。但不能据此断言本次手机一定在哪一秒丢了 socket，仓库记录没有真机网络抓包。

代码中可以直接确认的错误有三处：

1. `App` 的可见性回调只刷新列表和扩展，没有读取当前会话正文。push 重连的 `ready` 也只调用 `refreshOpenRuntime`，`fields=runtime` 不含消息。
2. `listeningIdRef` 只是本地“已经开始监听”的标记，无法证明 run reader 仍健康；按它跳过续听会保留半开连接。隐藏期间收过一次心跳也不能证明页面状态完整。
3. `applyTail` 重建时无条件保留 live 行。若挂起期间错过 `message_end` / `agent_end`，即使拿到已结束的快照，旧 partial 和运行中的工具仍可能被附加回来。原来的 `pagehide` 还会在退避后重开 push，缺少等待 `pageshow` 的状态。

## 修复

- 把前台 45s 探活和恢复后的数据协调分开。可见、online、bfcache pageshow 和 push ready 都能触发当前正文协调，不依赖隐藏时长或心跳。
- 取消旧 run reader，再取现有会话 GET 的 tail；保留已加载历史、索引、滚动意图和 compact 偏好。仍在运行则携带已应用的 Last-Event-ID 续听，绝不重新提交 prompt。
- idle 快照清理临时 partial、运行中的工具/轨迹/请求以及 stopping。失败时保留已显示内容，网络错误退避重试；切会话或分支会使旧任务失效。
- push 生命周期恢复立即换连接，不继承失败退避；pagehide 关闭两条订阅，pageshow 再恢复。
- 检查已有耗时显示时也修正了新请求尚未落盘时沿用上一轮开始时间的问题，避免把中间闲置时间算进新一轮。

## 回归与证据

新增浏览器测试在连接不报错、没有等待 45s 的条件下，直接发送恢复信号。修复前 `visibilitychange` 用例等待 15s 仍有 **0 次正文协调请求**，稳定失败；修复后 visibilitychange、pageshow、online 三种路径都显示唯一最终答案，旧 partial 与停止按钮消失。

另覆盖 pagehide 期间不重开连接、仍在运行时携带原游标续传、恢复后继续增量显示且不重发 prompt，以及首轮只有 live 节点、尚无历史 entries 的恢复。模型层测试确保清理终态不丢已加载历史和索引。

最终验证（2026-09-27）：

- `cd web && bun run typecheck && bun run build`：通过。
- `go test -tags embed -count=1 ./...`：通过，包含 Bun 单元测试和 117 条隔离浏览器用例，0 失败、0 跳过。
- `cd web && KI_WEBKIT_EXECUTABLE=/tmp/ki-webkit-libs/run-webkit bunx playwright test --project=webkit-scroll --project=firefox-scroll --project=webkit-compact-touch`：54 条通过。本机 WebKit 默认启动器缺少动态库，使用已有独立 WPE 启动器，不修改测试断言。
- `cd web && bun run test:perf`：6 条通过，独立于完整回归运行。

浏览器模拟生命周期不等于真实手机锁屏/进程冻结测试。

通过 `scripts/run.sh` 重建并重启真实配置的开发服务后，打开关联原始 session，在 390px 触屏布局中核对 8 条请求的导航，触发可见性恢复后阅读位置偏移为 0px，页面无异常。

## 教训

验收条件必须落在用户可见结果上：“最终答案已显示且状态正确”，不能停在“重连请求发出”。空闲守卫、生命周期恢复、权威快照协调是互补环节；只缩短阈值或检查 bundle 中存在某个常量，不足以证明恢复成功。

收到“仍旧无效”的反馈，应把原复现变成能失败的端到端断言，再修改实现。根因文档要区分可从代码和测试确认的事实，与没有真机证据的网络推断。
