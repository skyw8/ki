范围只包括执行、输出、状态、格式、并发和交互；暂不包括安全、权限和 sandbox。

## Codex apply_patch

参考：`/data/hgy/codex/codex-rs/apply-patch` 及其在 `codex-rs/core/src/tools/handlers/apply_patch.rs` 中的集成。

Ki 已有 add / delete / update / move、空白与 Unicode 标点宽松匹配，以及涉及路径的变更串行化；以下只记录仍值得借鉴的部分。

### 第一阶段：执行正确性

- [ ] 在第一次写盘前完成整份 patch 的预检：解析全部操作、解析并规范化源路径、读取所有原文件、定位所有 hunk，并计算每个文件的最终内容；同时拒绝多个操作指向同一源路径。这样能在写盘前发现缺文件、重复目标和上下文不匹配等确定性错误。
- [ ] 预检产物使用结构化 change set，至少包含绝对路径、操作类型、旧内容、新内容、move 目标和 unified diff，执行阶段直接消费该结果，避免校验和落盘各自解释一次 patch。
- [ ] 不把预检描述成跨文件事务：Codex 仍然逐项落盘，I/O 竞态、磁盘写入或删除失败时仍可能只完成前缀。若需要真正的全有或全无，应另行设计临时文件、原子替换与回滚协议。

### 第二阶段：部分提交与结果状态

- [ ] 像 Codex 的 `AppliedPatchDelta` 一样按执行顺序记录已确认落盘的 add / delete / update / move；记录被覆盖的旧内容，使成功结果、失败结果和后续 diff 跟踪使用同一份事实来源。
- [ ] 失败结果携带“已提交前缀”和 `exact` 状态。普通失败可精确说明已经发生的变更；若写入可能已截断、删除后的状态无法确认等，则标记为不精确，不虚构回滚成功。
- [ ] 将结构化 delta 放入工具结果和现有事件链，模型只接收简短摘要，session / WebUI 可据此展示实际变更；不要只依赖 `A/M/D path` 文本反推状态。

### 第三阶段：内容保真与流式预览

- [ ] 更新文件时保留原有 LF、CRLF、单独 CR 及混合换行；新增行沿用文件首选换行。当前实现会统一改成 LF，可能产生与实际修改无关的大 diff。尾部换行策略需显式定义并加入测试。
- [ ] provider 能提供 freeform 参数 delta 后，引入增量 patch parser，在模型生成期间产出文件 change 预览；事件按固定间隔节流并保证结束时发送最终快照，供终端和 WebUI 复用。该预览只是未执行状态，必须与最终 committed delta 区分。

### 后续扩展与验证

- [ ] 若引入远程或虚拟 workspace，再把直接 `os` 调用抽象为可注入文件系统与路径标识；Codex 的 environment ID 只在多执行环境确有需求时跟进，当前不单独实现。
- [ ] 补齐针对重复源路径、跨文件预检失败、落盘中途失败、delta 精确性、LF / CRLF / CR / 混合换行，以及任意分块流式输入的场景测试。

## Codex

参考：`/data/hgy/codex`。

### Unified exec

- [ ] 将“等待多久返回”和“命令最多运行多久”拆开：等待到期返回 live session，运行上限才终止进程。
- [ ] 提供与 `write_stdin` 等价的继续接口，支持轮询、写 stdin 和获取最终退出状态。
- [ ] 支持 TTY、显式 shell/login、环境变量和输出预算等执行参数。
- [ ] 为同一 session 保存必要的 shell environment snapshot，而不是每次仅重新执行 login shell。
- [ ] 扩展 `shellSpec` 的解释器类型和参数构造，覆盖 Unix sh/zsh、Windows CMD 和显式 shell 路径。该项只在出现对应使用需求时实施，不要求增加多个模型可见工具。

### 文件变更与并发

- [ ] 文件工具结果增加机器可读状态，同时保留简短的模型可读摘要。
- [ ] 将只读工具和文件变更工具显式分类：只读操作可并行，同一路径的变更必须串行。
- [ ] 为取消、timeout、后台完成和长任务建立跨工具统一的结构化事件。

### 可选工具

- [ ] `Plan`：为长任务和 WebUI 提供结构化步骤及状态；优先级中。
- [ ] `RequestUserInput`：WebUI 需要结构化选项交互时引入；优先级中。
- [ ] `ViewImage`：现有 Read 已能读图，先完成缩放；优先级低。
- [ ] `ToolSearch`：工具数量显著增长后再按需加载；优先级低。
- [ ] `Agent` / 多代理：单 agent 生命周期稳定后再评估；优先级低。
- [ ] `Sleep` / `CurrentTime`：只有需要无副作用等待或取时才引入；优先级低。
